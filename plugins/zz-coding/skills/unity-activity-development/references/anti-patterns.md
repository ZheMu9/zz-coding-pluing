# Unity Activity Anti-Patterns

本文档总结 Unity 活动开发中最常见的坏味道，以及每种情况更稳妥的最小修法。目标不是追求一次性改到“最优架构”，而是帮助 Agent 快速识别风险并给出低成本优化建议。

## 1. Panel 里直接写业务规则

### 1.1 坏味道

- `Panel` / `PopupPanel` 里直接判断奖励可领、阶段是否完成、活动是否结束
- 按钮点击后由 UI 直接修改 `Data`
- UI 刷新方法里同时处理展示和业务流程

### 1.2 风险

- 面板越来越重
- 相同业务规则在多个面板重复
- 后续加 TV / Popup / 子面板时容易不一致

### 1.3 最小修法

- 把判断下沉到 `Manager`
- `Panel` 只调用 `BuildViewData()` 或业务入口方法
- `Panel` 只保留绑定、刷新、动画逻辑

## 2. UI 层重复计算同一状态

### 2.1 坏味道

- `RefreshTopInfo()`、`RefreshReward()`、`RefreshButtons()` 都各算一遍同一个状态
- 同一个“是否可点击”“是否显示红点”分散在多个函数

### 2.2 风险

- 改一个逻辑要改很多处
- 不同刷新入口结果不一致
- 很难查出某个 UI 为什么状态不对

### 2.3 最小修法

- 增加 `ViewData`
- 在 `Manager.BuildViewData()` 中一次性构造展示结果
- 各个刷新函数只消费 `ViewData`

## 3. 真实数据改完后才开始播表现

### 3.1 坏味道

- 先扣次数 / 扣血 / 改阶段
- 再打开 TV 面板或播放 Timeline
- 动画读到的已经是变化后的值

### 3.2 风险

- 动画起点不对
- HP 跳变、奖励回放错位
- “看起来像逻辑错了”，其实是时序错了

### 3.3 最小修法

- 引入 `PresentationData`
- 先 `Clear()`
- 在修改真实数据前 `SyncFromRealData()`
- 表现面板优先读快照

## 4. 刷新入口太散

### 4.1 坏味道

- 打开面板时刷新一套
- 推包后又手动刷一套
- 倒计时、领奖、结算再各刷一套

### 4.2 风险

- 某个控件很容易漏刷新
- 新增一个状态时需要在多个入口补调用
- 维护成本高

### 4.3 最小修法

- 固定一个 `RefreshAll()` 主入口
- 再拆 `RefreshTopInfo()`、`RefreshButtons()`、`RefreshRewards()` 等局部刷新
- 不要在按钮回调中散落直接改多个控件

## 5. Manager 什么都做，但没有分区

### 5.1 坏味道

- `Manager` 里初始化、查询、动作执行、UI 协调全混在一起
- 函数顺序没有组织，越写越长

### 5.2 风险

- 新人很难理解入口
- 想拆又不知道从哪里拆
- 一改就容易误伤别的逻辑

### 5.3 最小修法

- 先按职责分区，不一定马上拆类
- 建议先分为：
  - `Init`
  - `Query`
  - `Action`
  - `UI`
- 先把边界理清，再考虑是否抽独立类

## 6. Data 承担太多流程控制

### 6.1 坏味道

- `Data` 里塞了大量业务方法
- `Data` 除了状态还负责流程推进、奖励判断、配置查表

### 6.2 风险

- 数据对象职责变混乱
- 难以判断“这个逻辑到底属于状态还是业务”
- UI 和 Manager 都可能直接绕过边界访问它

### 6.3 最小修法

- `Data` 保留运行态和轻量派生属性
- 复杂判断和动作移动到 `Manager`
- 配置访问可以保留，但流程控制尽量不要放 `Data`

## 7. TV / Popup 面板直接依赖实时 Data

### 7.1 坏味道

- TV 面板里大量直接读取 `Data`
- 动画期间 `Data` 继续变化
- 关闭再打开时状态容易串

### 7.2 风险

- 动画不稳定
- 表现结果受外部刷新影响
- 调试很难复现

### 7.3 最小修法

- TV 面板优先读 `PresentationData`
- `Data` 只作为兜底
- 关闭面板时清理表现状态

## 8. 为了“更优雅”过早上 Presenter / MVVM

### 8.1 坏味道

- 代码刚开始乱，就立刻想拆成很多层
- 没有明确收益，也开始造 `Presenter`、`Service`、`VM`

### 8.2 风险

- 类变多了，但问题没减少
- 项目风格和现有代码脱节
- 团队后续不一定会照着用

### 8.3 最小修法

- 先判断是否真的需要额外层
- 优先顺序通常是：
  1. 收口刷新
  2. 增加 `ViewData`
  3. 增加 `PresentationData`
  4. 最后再决定是否抽 `Presenter`

## 9. 一个方法既改状态又直接操作多个 UI

### 9.1 坏味道

- 点击事件里同时：
  - 改 `Data`
  - 改红点
  - 改文案
  - 改按钮状态
  - 播动画

### 9.2 风险

- 行为耦合严重
- 同样逻辑很难复用
- 以后插入新流程会很痛苦

### 9.3 最小修法

- 点击事件只调用业务入口
- 业务入口负责改状态
- UI 统一走刷新方法
- 表现统一走表现入口

## 10. 没有区分“真实状态”和“展示状态”

### 10.1 坏味道

- 文案、红点、倒计时、按钮状态全部直接从 `Data` 现算
- 面板显示依赖很多临时判断

### 10.2 风险

- UI 和业务边界不清
- 很难做缓存、动画、过渡态
- 重构时经常牵一发动全身

### 10.3 最小修法

- 真实状态放 `Data`
- 展示状态放 `ViewData`
- 异步表现状态放 `PresentationData`

## 快速判断表

| 现象 | 最优先改法 |
| ---- | ---------- |
| Panel 很重 | 抽 `ViewData` |
| TV/动画错位 | 加 `PresentationData` |
| 刷新常漏 | 收口 `RefreshAll()` |
| Manager 很乱 | 先按职责分区 |
| Data 太聪明 | 业务回收到 `Manager` |
| 想上大重构 | 先问是否真的必要 |

## 推荐回答格式

当 Agent 识别到这些坏味道时，建议按下面格式回答用户：

1. 先指出当前最核心的坏味道
2. 说明它为什么是问题
3. 给出最小修法，而不是最大重构方案
4. 说明这一步改完能解决什么
5. 再补一句“如果继续优化，下一步是什么”
