# Unity Activity Review Output Template

本文档用于规范 Agent 在审查 Unity 活动代码、给出重构建议、或分析活动架构问题时的输出格式。目标是让回答更稳定、可执行、便于团队直接采用。

## 适用场景

适用于下面这些请求：

- “帮我 review 这个活动代码”
- “这个活动结构哪里有问题”
- “这段活动代码怎么优化”
- “给我一个低风险重构建议”
- “这套活动代码有哪些风险”

## 总体原则

回答时优先遵循：

1. 先讲问题，再讲方案
2. 先讲最重要的问题，不要先写大段背景
3. 优先给最小改法，不先给大重构蓝图
4. 要明确指出问题属于哪一类
5. 结尾再补后续可选优化

## 推荐输出结构

建议按下面结构回答：

```markdown
## 核心问题

1. [问题标题]
   - 现象：
   - 风险：
   - 建议：

2. [问题标题]
   - 现象：
   - 风险：
   - 建议：

## 建议改动顺序

1. 第一步先做什么
2. 第二步再做什么
3. 第三步如果继续优化再做什么

## 适合当前项目的落地方式

- 保留什么
- 新增什么
- 暂时不要做什么

## 验证点

- 主流程验证
- 边界流程验证
- 回归风险验证
```

## 问题分类词汇

当 Agent 识别问题时，优先用这些分类词汇：

- `展示层承载业务`
- `刷新入口分散`
- `真实数据与表现时序错位`
- `Manager 职责过重`
- `状态边界不清`
- `展示状态与真实状态混用`
- `重复状态计算`
- `过早抽象`

这样输出会比“代码有点乱”“建议重构一下”更明确。

## 推荐问题写法

### 好的写法

```markdown
1. TV 面板直接依赖实时 Data，导致表现时序容易错位
   - 现象：攻击后真实 HP 先变化，动画再读取 Data，导致过渡起点错误
   - 风险：HP 动画跳变、表现与结算不同步
   - 建议：先补 PresentationData，让 TV 面板优先读快照
```

### 不推荐的写法

```markdown
1. 这里写得不太好，建议优化一下架构
```

问题要具体到“哪类问题 + 为什么有风险 + 最小修法”。

## 推荐改动顺序写法

当用户问“先怎么改”时，优先用这种格式：

```markdown
## 建议改动顺序

1. 先收口刷新入口，减少状态漏刷
2. 再把主面板展示判断下沉为 ViewData
3. 如果存在 TV / Timeline 演示，再补 PresentationData
```

### 原则

- 一次只引入一个新抽象
- 每一步都要能独立产生收益
- 不要求用户必须一次改完

## 推荐“适合当前项目的落地方式”写法

这个部分要避免空泛，建议明确写：

- **保留什么**：例如继续保留 `Manager + Panel`
- **新增什么**：例如增加 `BuildViewData()` 或 `PresentationData`
- **先别做什么**：例如暂时不要强拆 `Presenter`

示例：

```markdown
## 适合当前项目的落地方式

- 保留现有 `Manager + Panel` 主结构，不做大框架迁移
- 在 `Manager` 内增加 `BuildViewData()`，统一主面板展示状态
- 对 TV / Timeline 表现增加 `PresentationData`
- 暂时不要引入独立 `Presenter`，否则收益不明显
```

## 推荐验证点写法

不要只写“测一下”，建议明确给出：

```markdown
## 验证点

- 主流程：打开面板、执行一次主要玩法、领奖、关闭面板
- 边界流程：活动结束时打开面板、倒计时归零时刷新、重复点击按钮
- 表现流程：真实数据更新后，TV / Popup 是否仍能正确播放旧状态到新状态的过渡
```

## 用户问“要不要重构”时的推荐回答方式

优先回答：

1. 现在最值得动的一层是什么
2. 这一层改了能解决什么
3. 为什么不建议一步到位大重构
4. 如果未来继续演进，下一层是什么

## 用户问“有没有问题”时的推荐回答方式

不要只回答“有一些问题”。

优先回答：

1. 最严重的问题是什么
2. 它会造成什么具体后果
3. 最小修法是什么

## 推荐收尾模板

回答最后建议尽量收束成：

```markdown
如果只做一轮低风险优化，建议先做两件事：

1. [第一件事]
2. [第二件事]

这样可以先把最容易出错的部分稳定下来，后面再决定要不要继续拆结构。
```

## 简版模板

如果用户只想要简短建议，可以用这个短模板：

```markdown
## 核心问题

1. [最主要问题]
2. [第二主要问题]

## 最小改法

1. [先做什么]
2. [再做什么]

## 暂时不要做

- [不建议马上做的事]
```
