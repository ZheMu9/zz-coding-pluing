# Unity Activity Refactor Checklist

本文档用于判断一个已有 Unity 活动应该先做哪类优化。目标不是一次性“重构成最漂亮的结构”，而是帮助 Agent 选择**最小、最稳、最贴近当前项目**的改法。

## 使用方式

按顺序检查下面问题：

1. 先判断主要痛点属于哪一类
2. 再决定先抽 `ViewData`、先加 `PresentationData`，还是先收口刷新
3. 最后给出最小改动顺序

如果同时命中多个问题，优先处理：

1. 异步表现错位
2. 刷新入口混乱
3. 面板业务判断过重
4. Manager 职责过载

## 一、先判断主问题

### A. 面板里业务判断太多

典型症状：

- `Panel` / `PopupPanel` 中有大量 if/else
- 显隐、文案、按钮可点状态都在 UI 层计算
- 多个刷新函数重复算同一状态

优先改法：

- 先补 `ViewData`
- 把展示判断下沉到 `Manager.BuildViewData()`
- `Panel` 改成只消费展示结果

不要先做：

- 不要一上来拆复杂 `Presenter`
- 不要先动数据结构

### B. TV / 动画 / 结算回放和真实数据错位

典型症状：

- 真实数据已经更新，但动画还需要旧状态
- TV 面板读到的是“变化后的值”
- HP、奖励、阶段切换动画起点不对

优先改法：

- 先加 `PresentationData`
- 在执行动作前 `Clear()`
- 在改真实数据前 `SyncFromRealData()`
- TV / Popup 面板优先读 `PresentationData`

不要先做：

- 不要先把逻辑硬拆成多个类
- 不要让表现面板直接依赖实时 `Data`

### C. 刷新入口过多，改一个地方会漏别处

典型症状：

- 打开面板、推包、领奖、倒计时、结算都各自刷新一套
- 某个控件刷新依赖多处手动调用
- 新增一个状态后，经常漏改

优先改法：

- 先收口刷新入口
- 固定 `RefreshAll()` 为主入口
- 再拆分 `RefreshTopInfo()`、`RefreshButtons()`、`RefreshRewards()` 等局部刷新

不要先做：

- 不要先抽数据层
- 不要先大规模挪方法

### D. Manager 太大，但还看不清该怎么拆

典型症状：

- `Manager` 几百行甚至上千行
- 初始化、查询、执行、UI 协调混在一起
- 想拆，但不知道拆哪里最值

优先改法：

- 先按职责分区，不一定先拆文件
- 把方法分成：`Init`、`Query`、`Action`、`UI`
- 再观察哪一块最稳定、最适合独立抽出

不要先做：

- 不要为“看起来更优雅”而强拆多个新类
- 不要在没明确收益前就上完整 MVVM

## 二、判断是否需要 ViewData

满足任意 2 条，建议引入 `ViewData`：

- 面板里有 3 个以上展示状态判断
- 同一业务状态在多个局部刷新函数里重复计算
- 文案、显隐、红点、按钮可点状态相互耦合
- 同一组展示结果会被主面板和子面板复用

适合放进 `ViewData` 的内容：

- 文案字符串
- 按钮是否可点击
- 红点是否显示
- 标签 / 徽标 / 阶段显隐
- 倒计时格式化结果

不适合放进 `ViewData` 的内容：

- 修改数据的方法
- 网络请求逻辑
- 复杂流程控制

## 三、判断是否需要 PresentationData

满足任意 1 条，就优先考虑 `PresentationData`：

- 数据会先变化，表现后播放
- 表现期间真实数据还会继续变化
- TV / Timeline / Spine / DOTween 需要旧值做过渡
- 面板关闭后异步表现还未结束

适合放进 `PresentationData` 的内容：

- HP / Score / Count 的表现起始值
- 当前阶段和下一阶段 ID
- 是否击杀 / 是否升级 / 是否触发演示
- 当前表现需要的奖励或品质信息

不适合放进 `PresentationData` 的内容：

- 真实业务规则
- 配置访问
- 长期持久化状态

## 四、判断是否只需要“方法收口”

如果问题主要是“逻辑散”，但还没到要拆类，优先做方法收口。

典型做法：

```csharp
RefreshAll();
RefreshStaticView();
RefreshRuntimeView();
RefreshRewardState();
RefreshCountdown();
```

适用场景：

- 结构大体还能接受
- 主要问题是调用时机太散
- 团队短期更重视低风险改法

## 五、推荐决策表

| 主要问题 | 第一优先 | 第二优先 | 暂时不要做 |
| ---- | ---- | ---- | -------- |
| 面板判断过重 | `ViewData` | 刷新收口 | 强拆 `Presenter` |
| TV/动画错位 | `PresentationData` | 刷新收口 | 直接读实时 `Data` |
| 刷新很乱 | 刷新收口 | `ViewData` | 大规模拆类 |
| Manager 很大 | 职责分区 | 提炼稳定块 | 完整 MVVM |

## 六、最小改动顺序模板

当 Agent 需要给出“怎么改”时，优先用下面格式回答：

```text
1. 保留现有主结构不动
2. 先处理最痛的那一层
3. 只增加一个新抽象（ViewData / PresentationData / 刷新入口）
4. 等逻辑稳定后再考虑下一步
```

## 七、回答用户时的推荐输出

当用户问“这段活动代码怎么优化”时，优先回答：

1. 当前主问题属于哪一类
2. 为什么先做这个，而不是先做别的
3. 最小改动涉及哪些类
4. 改完能解决什么问题
5. 下一步如果继续优化，建议是什么

## 八、一个贴近当前项目的判断示例

如果一个活动具备这些现象：

- `Manager` 里已经有较多业务入口
- TV 面板会播放 Timeline / 动画
- 主面板和 TV 面板都依赖运行态数据
- 攻击后真实 HP 会立刻变化

那么优先顺序通常是：

1. 先加 `PresentationData`
2. 再让 TV 面板优先读快照
3. 再补 `BuildViewData()`
4. 最后才考虑是否继续拆 `Presenter`

这通常比“一步到位重构架构”更稳。
