# 直觉层决策问题协议

## 概述

AI完成逻辑层检查后，不直接给最终结论，而是生成结构化决策问题交给制作人判断。这是双层协作的核心机制——**AI做逻辑，人做直觉**。

## 决策问题分类

### Gate（门控）

**定义**：AI无法替代人判断的核心问题。
**触发**：涉及"好不好玩"、"目标感是否清晰"、"节奏对不对"等需要直觉的判断。
**行为**：必须等人回答才能继续。

**典型场景**：
- Purpose 引擎发现设计目的可以多种理解 → 问制作人哪种理解是对的
- Rhythm 引擎检测到情绪平原 → 问制作人这段体验的目标感是否足够

### Flag（标记）

**定义**：AI发现了逻辑问题，请人确认是否真的是问题。
**触发**：引擎检测到可能的违规，但AI无法确定是有意为之还是真的有问题。
**行为**：人可以推翻AI结论。

**典型场景**：
- RedLine 引擎发现一个系统不服务核心循环 → 问制作人是否有意为之
- Value 引擎检测到付费设计可能影响公平感 → 问制作人是否认同

### Sense（直觉）

**定义**：纯直觉判断，无法量化。
**触发**：涉及"有没有意思"、"这个体验对不对"等完全依赖经验的判断。
**行为**：人的回答直接记录为制作人裁决，不做二次质疑。

**典型场景**：
- 成长节奏的波峰波谷间隔是否"感觉对"
- 某个系统的 UE 是否"清晰易懂"

## 生成规则

1. **每轮最多3个问题**——不一次性轰炸，优先问影响最大的
2. **优先级顺序**：先 Gate → 后 Flag → 后 Sense
3. **提供选项**：尽可能给A/B/C选项，降低决策负担
4. **附带事实依据**：每个问题附上AI检测到的具体事实，人只需判断"是否认同"
5. **不重复提问**：同一个问题不同引擎都发现了，合并为一个决策问题

## 决策问题模板

### Gate 模板

```markdown
## 🔒 Gate 决策 #N

**引擎来源**：[引擎名称]
**检测事实**：[AI发现的具体事实，引用方案原文]
**问题**：[需要人判断的问题]

- A) [选项A — 通常是"问题存在，需要修改"]
- B) [选项B — 通常是"这是有意设计，不需要改"]
- C) 不确定，需要做原型/AB test验证
```

### Flag 模板

```markdown
## 🚩 Flag 标记 #N

**引擎来源**：[引擎名称]
**检测事实**：[AI发现的逻辑问题]
**AI判断**：[AI认为这是什么问题，严重度]
**需要确认**：你认同这是一个问题吗？

- A) 认同，需要修改
- B) 不认同，这是有意为之（请说明原因）
```

### Sense 模板

```markdown
## 💡 Sense 直觉 #N

**引擎来源**：[引擎名称]
**背景**：[相关的方案内容摘要]
**问题**：[需要直觉判断的问题]

请直接给出你的判断。
```

## 人回答后的AI行为

| 人的回答 | AI下一步 |
|---------|---------|
| 认同问题存在 | 自动生成优化建议（逻辑层能做的部分） |
| 不认同，给出理由 | 记录为"制作人裁决"，在报告中标注理由 |
| 不确定 | 标记为"待验证项"，建议做原型或AB test |
| 选择了某个选项 | 按选项方向继续推进分析 |

## 多轮决策

如果第一轮3个问题回答后，仍有重要的未决问题：
1. 基于第一轮回答，更新分析结论
2. 生成第二轮决策问题（仍然≤3个）
3. 重复直到所有关键判断点都已覆盖

一般不超过3轮。超过3轮说明方案问题过多，建议推翻重来。

## Optimize 模式下的协议裁剪

`/game.optimize` 模式对本协议做了严格裁剪：**只使用 Gate，不使用 Flag 也不使用 Sense。**

### 裁剪规则

| 类型 | optimize 是否使用 | 理由 |
|------|:----------------:|------|
| Gate | ✅ | A/B 选择、冲突折中 |
| Flag | ❌ | optimize 的前提是信任审核报告；允许 Flag 意味着主代理能推翻审核结论，这会把 optimize 拉回 review 的职责，破坏命令正交 |
| Sense | ❌ | optimize 是快速补丁，不做体验直觉判断；直觉判断是 craft 和 review 的职责 |

### Gate 的两种来源

在 optimize 模式下，Gate 问题只可能来自以下两种情况：

1. **A/B 备选选择**——主代理生成修复时判定"此修复动到价值排序里 ≥2 个维度"，于是生成 A/B 备选，让制作人拍板
2. **冲突折中**——主代理自 review 发现两个修复互相矛盾，让制作人决定保留哪个或折中

### Gate 批处理规则

- 所有 Gate 合并成一批提问，不混入其他类型
- 仍然遵循本协议的"每轮 ≤3 个问题"总规则
- 若总 Gate 数 >3，分轮优先级：**冲突折中 > 动到更高优先级价值维度的 A/B > 其他 A/B**
- 价值维度优先级参考 producer-methodology.md：公平感 > 社交生态 > 爽感 > 留存 > 付费

### 为何 optimize 的裁剪与 review/craft 不同

- review 是发现问题的模式，需要 Gate/Flag/Sense 全协议覆盖"要不要信 AI 的判断"和"人的直觉感受"
- craft 是从零设计的模式，需要 Gate 卡住方向、Sense 捕捉体验直觉
- optimize 的前提是"方向已定、问题已知、只差怎么修"，唯一需要人的地方就是权衡和冲突——这正是 Gate 的定义
