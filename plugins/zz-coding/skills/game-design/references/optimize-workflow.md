# Optimize 模式：补丁链路工作流

## 概述

`/game.optimize` 是 game-design skill 的补丁模式，用于基于**已有审核报告**对原方案生成定点修复方案并输出 diff。与 review/craft 不同，optimize 是**纯补丁式的**——它不发现新问题、不重新设计、不做迭代收敛，只负责回答"怎么修"这一个问题。

核心原则不变：**AI 做逻辑层（修复生成 + 跨修复冲突检测），人做直觉层（价值权衡裁决 + 冲突折中）。**

## 与 Review/Craft 的关系

```
review 负责："有什么问题" + "问题多严重"
optimize 负责："怎么修"
craft 负责："从零设计 + 内置审核迭代"
```

optimize 必须以一份已有审核报告为输入，不会自动触发 review。这保证了三条命令正交，避免 optimize 变成隐式的 review 替身。

**什么时候不该用 optimize**：
- 没有审核报告 → 先跑 `/game.review`
- 想改方案方向或核心循环 → 用 `/game.craft` 或从零开始
- 想要"审核 + 修复"一气呵成 → 仍然分两步跑 review 和 optimize，不要期待一个命令包办

## 五阶段工作流

```
输入：审核报告路径 + 原方案路径（均从 input/ 读取）
    ↓
阶段1：读取与校验
    ↓
阶段2：生成修复（主代理单 pass）
    ↓
阶段3：自 review（主代理单 pass，检测冲突）
    ↓
阶段4：批量 Gate 问答
    ↓
阶段5：合并完整方案 → 写出完整文档 + diff
```

### 阶段1：读取与校验

**目标**：确认输入完整，建立修复清单。

**执行方式**：主代理 opus 读取审核报告和原方案两份文档。

**必要校验**：
1. 审核报告路径存在且可读
2. 原方案路径存在且可读
3. 审核报告中至少存在一条 P0 或 P1 问题（若全是 P2 也可继续，但主代理应在输出开头说明"本次优化仅涉及 P2 级问题"）
4. 审核报告的审核对象文件路径与传入的原方案路径一致（防止误配）

**校验失败处理**：
- 缺文件 → 直接报错，不继续
- 审核对象不匹配 → 报错并提示 "审核报告审核的是 X，传入的方案是 Y，是否确认继续？"

### 阶段2：生成修复

**目标**：对审核报告中的每条问题生成修复方案。

**执行架构**：

```
主代理 opus
    读取：审核报告全部问题 + 原方案相关段落
    ↓
    单 pass 生成所有修复方案
        ├─ 执行性问题 → 单方案
        └─ 动 ≥2 价值维度 → A/B 备选
```

**为何单主代理串行（不做 Fan-out/Fan-in）**：
- optimize 的问题总数通常不多（审核报告里的 P0+P1），启动多子代理的成本高于收益
- 单主代理天然具备全局视角，跨修复一致性更好保证
- 与 review 的 Fan-out 架构不同，这是刻意的设计区分

### A/B 备选触发规则

**核心规则**：当且仅当修复方案涉及**价值排序里 ≥2 个维度的此消彼长**时，才生成 A/B 备选。

价值排序参考 producer-methodology.md：
> 公平感 > 社交生态 > 爽感 > 留存 > 付费

**判断示例**：

| 场景 | 是否生成 A/B |
|------|:------------:|
| 文案歧义或错字 | 否 |
| 纯数值校准（仅影响经济曲线） | 否 |
| 补充缺失的系统说明 | 否 |
| 修社交冲突但会降低爽感 | 是（A 保社交 / B 保爽感） |
| 修通胀但会触碰公平感红线 | 是（A 保公平 / B 保通胀控制） |
| 修付费点但可能影响留存 | 是（A 保留存 / B 保付费） |

**为何不总是生成 A/B**：
- 强凑 B 方案会降低方案质量并制造决策噪音
- A/B 在 optimize 中等价于一个 Gate 问题，必须有真实权衡才值得打扰制作人

**每个修复方案的必填字段**：
- 描述（怎么改）
- 原方案定位（引用哪一段）
- 对玩家分层影响（引用 producer-methodology.md 的四维正交分层）
- 对价值排序影响（点出动了价值排序里的哪些维度）

### 阶段3：自 review（冲突检测）

**目标**：检测同一份修复集合里是否存在互相矛盾的 diff。

**执行方式**：同一主代理对自己刚生成的全部修复做一次额外 pass。

**检测对象**：
1. 两个修复动到同一段原文但改动方向不一致
2. 修复 A 的收益被修复 B 抵消
3. 多个修复累积后某个引擎（特别是 Economy、Value）的状态比原方案更差

**冲突升级规则**：
- 发现冲突时，将冲突记录为一个新的 Gate 问题
- Gate 语义：
  > "修复 #N 与修复 #M 存在冲突：[冲突描述]。你倾向：(A) 保留修复 #N、(B) 保留修复 #M、(C) 我来折中描述"

**为何需要自 review**：
- 单主代理虽然有全局视角，但在专注生成单个修复时可能出现局部最优，忘记刚写过的其他修复
- 自 review 是对 B1 架构风险的最小补丁，成本仅为一个额外 LLM pass
- 哲学上仍是"AI 做逻辑完整性检查"，没有越界到人的直觉判断

### 阶段4：批量 Gate 问答

**目标**：把所有需要人拍板的问题一次性问完。

**Gate 问题来源（两种）**：
1. 阶段 2 生成的 A/B 备选
2. 阶段 3 自 review 发现的冲突

**批处理规则**：
- 所有 Gate 问题合并成一批，一次性提问
- 遵循 decision-protocol.md 的"每轮 ≤3 个问题"规则：若总 Gate 数 >3，分轮进行
- 分轮时优先级：**冲突折中 > 动到更高优先级价值维度的 A/B > 其他 A/B**
- 价值维度优先级参考 producer-methodology.md：公平感 > 社交生态 > 爽感 > 留存 > 付费

**Gate 问题模板（optimize 模式专用）**：

A/B 选择 Gate：
```markdown
## 🔒 Gate #N（A/B 选择）

**优化项**：[问题简述]
**来源**：[审核报告中的引擎 / 制作人决策 #N]
**为何需要你决定**：此修复动到价值排序里的 [维度1] 和 [维度2]，存在此消彼长

**方案 A**：[描述]
- 保：[维度1]
- 损：[维度2]

**方案 B**：[描述]
- 保：[维度2]
- 损：[维度1]

请选择：A / B / 自定义（请描述）
```

冲突折中 Gate：
```markdown
## 🔒 Gate #N（冲突折中）

**冲突项**：修复 #M 与修复 #K
**冲突描述**：[具体冲突]

请选择：
- A) 保留修复 #M，放弃修复 #K
- B) 保留修复 #K，放弃修复 #M
- C) 我来描述折中方案
```

### 阶段5：合并完整方案

**目标**：将所有修复合并回原方案，输出完整文档。

**执行方式**：主代理（opus）在 Gate 问答结束后执行。

**合并规则**：
1. 以原方案为基底，逐条应用修复
2. 制作人在 Gate 中选择了 A/B 的，按选择结果应用
3. 制作人提供了自定义描述的，按自定义内容修改
4. 所有媒体引用保留原始路径不变
5. 新增内容中如需建议图表，以文字占位符标注（如 `[建议插入：XX 流程图]`）

**输出**：
- `output/optimize-YYYY-MM-DD.md`（完整方案）
- `output/optimize-diff-YYYY-MM-DD.md`（变更 diff）

两个文件的模板见 [templates.md](templates.md) 的 optimize 输出模板章节。

## 与 decision-protocol.md 的衔接

optimize 模式对决策协议的三种类型做了严格裁剪：

| 类型 | optimize 模式是否使用 | 原因 |
|------|:-------------------:|------|
| Gate | ✅ | A/B 选择、冲突折中 |
| Flag | ❌ | 前提是信任审核报告，允许 Flag 会把 optimize 拉回 review 的职责 |
| Sense | ❌ | optimize 是快速补丁，不做体验直觉判断 |

详细的裁剪说明见 decision-protocol.md 的 "Optimize 模式下的协议裁剪" 章节。

## 异常处理

| 情况 | 处理方式 |
|------|---------|
| 审核报告缺失 | 报错，提示先跑 `/game.review` |
| 审核报告审核对象与原方案不匹配 | 报错并要求用户确认是否继续 |
| 审核报告里没有任何 P0/P1，仅有 P2 | 继续执行，但在输出开头说明本次仅涉及 P2 级优化 |
| 阶段 3 检测到超过 3 个冲突 | 说明原方案根本性问题较多，建议用户重新审核或直接进入 craft 模式重构，而非继续硬修 |
| 单轮 Gate 问题 >3 | 按"冲突折中优先 > 高价值维度优先"分轮 |
| 制作人在 Gate 回答中选择"自定义"或"C" | 主代理记录制作人的自定义描述为最终裁决，写入 diff 时按自定义描述修改 |
