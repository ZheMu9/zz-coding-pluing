# Craft 模式：从零设计方案工作流

## 概述

`/game.craft` 是 game-design skill 的设计模式，用于从零开始构建策划方案。与 review/optimize 不同，craft 是**生成式**的——但它不是凭空生成，而是**在制作人方法论框架内**，通过结构化的信息收集 → 设计 → 内置审核 → 迭代循环来产出方案。

核心原则不变：**AI 做逻辑层（草稿生成 + 完整性检查），人做直觉层（方向判断 + 体验裁决）。**

## 与 Review/Optimize 的关系

```
craft 模式内部 = 信息收集 + 设计生成 + 自动触发 review
```

craft 产出的方案在交付前会自动经过 6 引擎检查（裁剪后），形成"设计即审核"的闭环。

## 四阶段工作流

```
阶段1：信息收集（收敛）
    ↓ 制作人回答 Gate 问题
阶段2：MVP 草稿生成（发散）
    ↓ 制作人 Sense 判断
阶段3：内置审核（收敛）
    ↓ 引擎检查 + 制作人 Gate/Flag 判断
阶段4：迭代优化（发散→收敛）
    ↓ 重复阶段3直到通过
    → 输出最终方案
```

### 阶段1：信息收集

**目标**：在动手设计前，收集充分的约束条件和设计意图。

**执行方式**：主代理（opus）基于 [craft-info-gathering.md](craft-info-gathering.md) 生成结构化问题。

**关键规则**：
- 不要假设，不明确的必须问
- 优先问 Gate 级问题（方向性的），再问 Sense 级（体验偏好的）
- 每轮≤3个问题，信息收集不超过2轮
- 如果制作人给的信息很充分，可以跳过部分问题

**信息收集完成的标志**：
1. 设计目的可以用一句话说清楚
2. 目标玩家分层已明确
3. 在游戏框架中的位置已确认
4. 关键约束条件已知（时间、资源、技术限制）

### 阶段2：MVP 草稿生成

**目标**：快速产出一个"最小可审核"的设计草稿。

**执行架构**：

```
主代理 opus（综合信息 + 选择设计模式 + 定义草稿骨架）
    ├─→ 核心循环设计 子代理 sonnet
    ├─→ 数值框架设计 子代理 sonnet（如需要）
    └─→ 玩家体验流设计 子代理 sonnet
               ↓
    主代理 opus Fan-in → 组装 MVP 草稿
```

**MVP 草稿必须包含**：
1. **一句话设计目的**
2. **活动循环描述**（体力→代币→游玩→奖励的完整链条）
3. **体力消耗预期**（一轮消耗多少体力？3天内免费体力能完成几轮？付费点在哪？）
4. **情绪曲线草图**（至少标出压力期和释放期的交替，体力耗尽=天然付费决策点）
5. **玩家分层影响预判**（中坚层体验、大R体验、免费层体验）
6. **与现有系统的接口**（目标活动如何改变钓场鱼种？代币从钓鱼的哪个环节产出？）

**MVP 草稿刻意不包含**：
- 详细数值表（留给迭代阶段）
- 完整美术需求（留给迭代阶段）
- 边界情况处理（留给审核发现）

**设计模式库参考**：见 [project-context.md](project-context.md)

**MVP 生成后的 Sense 问题**（必问）：
```
💡 Sense 直觉 #1
这个草稿的核心循环，你觉得有没有意思？能不能让玩家产生目标感？
- A) 方向对了，继续深化
- B) 有潜力但核心循环需要调整（请说明）
- C) 方向不对，推翻重来
```

### 阶段3：内置审核

**目标**：用 6 引擎检查 MVP 草稿，发现逻辑问题。

**执行方式**：与 `/game.review` 相同的引擎架构，但有以下调整：

| 差异点 | review 模式 | craft 模式 |
|--------|------------|-----------|
| 评分标准 | 按完整方案标准 | 按 MVP 标准（允许缺失细节） |
| 引擎裁剪 | 按方案类型 | 按 MVP 覆盖范围 |
| 问题严重度 | 正常评级 | 仅标记 P0（MVP 阶段只关注致命问题） |
| 决策问题 | 完整三类 | 侧重 Gate（方向性）和 Sense（体验性） |

**craft 内置审核的引擎裁剪规则**：

| MVP 覆盖内容 | 必启引擎 | 可选引擎 |
|-------------|---------|---------|
| 有核心循环 + 情绪曲线 | Purpose, Rhythm, RedLine | — |
| 有玩家分层预判 | + Segment | — |
| 有资源/经济设计 | + Economy | — |
| 有付费设计 | + Value | — |

### 阶段4：迭代优化

**目标**：基于审核结果和制作人裁决，逐步深化方案。

**迭代内容**：
1. 修复内置审核中的 P0 问题
2. 根据制作人裁决调整设计方向
3. 逐步补充：详细规则 → 数值框架 → 玩家体验流 → 边界情况
4. 每轮迭代后重新跑内置审核

**迭代终止条件**：
- 内置审核无 P0 问题
- 制作人对核心体验的 Sense 判断为"方向对了"
- 一般不超过 3 轮迭代（超过 3 轮说明初始方向有问题，建议回到阶段 1）

**输出**：使用 templates.md 中的 `/game.craft` 输出模板。

```
你是核心循环设计专家，负责为游戏系统设计核心玩法循环。

## 你的方法论

重点关注：

- 第7章"红线与误区"——三条红线，尤其是"不做冗余系统"

## 设计约束
[从信息收集阶段获取的约束条件]

## 设计模式参考
[从 project-context.md 中选取的相关模式]

## 游戏核心框架
本游戏的核心循环类似 Coin Master，用钓鱼替代老虎机。体力是核心货币（玩家每天消耗完），卖体力是主要变现手段。
经济链条：体力 → 钓鱼 → 活动代币 → 参与循环活动 → 奖励。
所有活动都必须接入体力经济，否则脱离核心付费链条。

## 要求
1. 确定活动属于哪种核心模式：C1（钓鱼概率触发→进度奖励）/ C2（活动代币消耗→游玩→奖励）/ C3（随机即时反馈）/ C4（对抗结算）
2. 设计活动循环，必须接入体力经济（C2：体力→钓鱼→活动代币→活动；C1：体力→钓鱼→概率触发）
3. 循环中必须有压力-释放交替，活动代币/体力耗尽是天然的付费决策点
4. 描述要"直觉式清晰"——如果需要一大段文字才能解释清楚，说明太复杂了
5. 标注体力消耗预期（一轮多少体力）和与现有系统的资源接口

## 输出格式
- 核心循环一句话描述
- 循环流程图（文字版）
- 压力-释放节奏标注
- 与现有系统的接口清单
```

### 数值框架设计子代理

```
你是数值框架设计专家，负责为游戏系统设计初步数值框架。

## 你的方法论
先阅读制作人方法论：[producer-methodology.md 路径]
重点关注：
- 第2章"成长节奏理论"——波峰波谷循环、重置策略
- 第3章"价值排序"——公平感的精确定义
- 第7章"红线与误区"——经济系统是"最难救"的高危系统

## 设计约束
[从信息收集阶段获取的约束条件]

## 要求
1. MVP 阶段只需要框架级数值，不需要完整数值表
2. 必须包含：体力→代币的转化比例、一轮活动的体力消耗量、代币→进度的消耗比例
3. 必须考虑：免费体力（3天周期内）能完成的轮次 vs 付费可达轮次、对应的礼包定价区间
4. 必须考虑：付费/免费玩家的差异体验、追赶机制
5. 标注需要后续 AB test 验证的数值假设

## 输出格式
- 资源流向图（文字版）
- 成长曲线形状描述
- 关键数值假设清单（标注置信度）
- 公平感风险评估
```

### 玩家体验流设计子代理

```
你是玩家体验流设计专家，负责设计玩家从进入到退出的完整体验路径。

## 你的方法论
先阅读制作人方法论：[producer-methodology.md 路径]
重点关注：
- 第1章"设计哲学"——"前10分钟就要有体验循环"
- 第4章"玩家模型"——四维正交分层，重点保护中坚层
- 第7章"红线与误区"——"前期过度披露"和"设计给自己玩"

## 设计约束
[从信息收集阶段获取的约束条件]

## 要求
1. 描述首次进入的体验流（前3分钟）
2. 描述一次完整循环的体验流
3. 标注情绪曲线的关键节点（压力点、释放点、惊喜点）
4. 为不同玩家分层标注体验差异
5. UE 必须"直觉式清晰"——新玩家无需文字引导就能理解

## 输出格式
- 首次体验流程（步骤 + 情绪标注）
- 单次循环体验流程
- 分层体验差异表
- UE 清晰度自检（是否需要文字解释？是否操作步骤过多？）
```

## 异常处理

| 情况 | 处理方式 |
|------|---------|
| 制作人信息不足以开始设计 | 追加一轮信息收集（最多追加1轮） |
| MVP 草稿被制作人推翻 | 询问推翻原因，回到阶段1重新收集方向性信息 |
| 3轮迭代后仍有 P0 | 建议制作人暂停，先做原型验证核心循环 |
| 设计目的与现有系统冲突 | 生成 Gate 问题，让制作人决定是调整新方案还是调整现有系统 |
